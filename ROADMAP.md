## Decisions

- 2026-10-14 ✱ Name **StrataFlow**, subdomain **flow.quaera.app**, public repo github.com/StanislavSidorovich/StrataFlow (owner's choice).
- 2026-10-14 ✱ Same stack and architecture as StrataSQL (pure TS core + React Flow canvas). D1 (React Flow vs bpmn-js) and D2 (bpmn-moddle vs own XML) to be confirmed in stage 0.
- 2026-10-14 ✱ BPMN XML is the interchange format with Bizagi; native `.bpm` is optional.
- 2026-10-14 ✱ Case domains mirror StrataSQL's (Library, Hotel, Online Shop, Hospital, Scooter Sharing, Football) so a student can see the data model and the process of the same business; later they can be linked.
- 2026-10-14 ✱ Modeling conventions = NOVA BPM Chapter 3 (Dumas et al. 2013) and the 7PMG from Chapter 4; Silver's Method and Style only where the course is silent. Chapter 5 (VA/BVA/NVA, waste, issue register) is a later analysis feature, not stage 1–3.
- 2026-10-14 ✱ **D1 = React Flow** (spike passed: pools, lanes, tasks with markers, events, gateways, data, sequence/message/data flows along DI waypoints, orthogonal routing after a move; real Bizagi exports look as in Bizagi). bpmn-js stays rejected (watermark, harder overlays).
- 2026-10-14 ✱ **D2 = bpmn-moddle 10** (MIT, plain licence without the bpmn.io watermark clause, parser only) for reading; our own mapping to FlowModel. Bizagi quirks handled: an empty "Main Process" pool in every file; lane x is relative to the pool (x = header width), y absolute. Writing BPMN: decide in stage 2 (moddle `toXML` likely).
- 2026-10-14 ✱ Brand icon: teal `#0d9488` mark (start event → task → gateway), SVG only for now; PNG icons for install later.
- 2026-10-14 ✱ Own cases only in the public repo; course cases only with the professor's permission; the graded group project never before grading.

- 2026-10-14 ✱ **Node placement: absolute coordinates** (as BPMN DI) and pool / lane / sub-process looked up from the shape's centre after every add or move (`place()` in `core/ops.ts`), not React Flow `parentId`. A pool move takes its lanes and nodes; a task move takes its boundary events; a sub-process move takes its content.
- 2026-10-14 ✱ The flow kind is chosen by the editor from its ends: annotation → association, data → data association, different pools (or a pool) → message flow, else sequence flow. The student draws "a line"; the linter later explains.
- 2026-10-14 ✱ Deleting a lane gives its room and its steps to the lane above (the one below for the first lane), so nothing on the canvas moves. Appending past a pool's end widens the pool.
- 2026-10-14 ✱ First visit opens the Library example (from `library-loan.flow.json`); later visits reopen what was there (localStorage). New and Open are undoable.

- 2026-10-14 ✱ **BPMN writer = bpmn-moddle `toXML`**, mapping in `core/bpmn/write.ts` mirrors the reader. A pool with steps gets a process named after it; lanes list every flow node in them, also inside sub-processes; data and annotations get their pool and lane from where they sit (BPMN has no lane for them); flows without stored waypoints are routed as the canvas draws them; a collapsed sub-process's content goes in a diagram of its own (as bpmn.io). "Lossless" = read(write(m)) equals m up to list order, plus waypoints for flows that had none; a second trip changes nothing.
- 2026-10-14 ✱ **An empty pool is a black box.** Every exported pool gets a process (Bizagi drops a pool without one); a process without steps reads back as a black box. Bizagi's empty "Main Process" pool is dropped only in Bizagi files. A start event stores `interrupting` only when false.
- 2026-10-14 ✱ **Export for Bizagi and bpmn.io at once** (after the owner's first Bizagi check): the drawing moves so the leftmost pool sits at x = 0 (Bizagi reads lane x relative to the pool, bpmn.io absolute; at 0 they agree; pools with other x still show shifted lanes in Bizagi); data objects only as DataObjectReference (Bizagi drew the bare DataObject a second time); each data association also written as a plain association along the same line (that is what Bizagi draws); label bounds where the canvas shows them. The reader reads Bizagi's bare drawn DataObject and merges its association with the data association.
- 2026-10-15 ✱ **Auto layout = elkjs layered per pool and per expanded sub-process, then rows per lane** (`core/layout.ts`). elkjs gives the columns and the order; each lane gets as many rows as its steps need, so lanes stay bands and nothing changes pool, lane or sub-process. Content starts 60 px right of the innermost lane strip (Bizagi writes lane names there). Pools are stacked in their order with a 60 px gap and made as wide as the widest. Data and annotations go in a row under the steps they are linked to, in the lane of the first one, but stay in their own pool or sub-process (BPMN keeps them there). Steps outside every lane in a pool with lanes (Bizagi allows it) get a band of their own below the lanes. A collapsed sub-process takes its hidden content along; boundary events keep their place along the host's lower border. All flows are routed again (stored waypoints dropped). elkjs (EPL-2.0, used unmodified as a library) loads on the first click only (1.4 MB chunk, precached for offline).
- 2026-10-15 ✱ **Group into sub-process makes an expanded sub-process round the selection** (content stays where it is, a start event on the left, end events on the right, what sits right of the selection moves right; the pool and holding sub-processes widen first, so nothing leaves its pool). One step reached from outside: start → that step. Several: start → exclusive gateway → each, after the user's yes. Each place reached outside gets an end event of its own inside (the branch keeps its condition and default); several places: an exclusive gateway after the sub-process repeats the choice with the same names and conditions (no merge gateway inside: it would join branches that carry conditions). The user is asked before gateways are added (they may need to be parallel). Message flows stay on the inner steps, data and boundary events come along; the sub-process takes the lane holding most selected steps. **Ungroup** puts the steps back, removes the "none" start and end events only when flows came in or went out, joins each flow in to each step after the start event and each flow out to each step before an end event (a branch keeps its own condition, so two branches may join the same two elements), moves message flows, data and notes on the sub-process to its first or last step; a collapsed sub-process's content is brought to where the sub-process was. It refuses a sub-process with boundary events, or flows in or out without a plain start or end event. The canvas no longer raises a selected shape above the others (a selected expanded sub-process covered its steps).

- 2026-10-15 ✱ **Model check (stage 3)**: `lintModel` in `core/lint.ts`, one pass per process level (a pool's top level, each sub-process, the free canvas; a boundary event sits on its host's level and reachability goes on through it). P02 reports only the cause: a step whose predecessor is already unreachable (or whose successor already has no way to an end) is left out, unless they are on one loop. A loop no flow leaves is P17, not P02 step by step. P07 matches a join with the nearest node with several ways out that every incoming branch comes from (walking back, not past the join); a task with several outgoing flows counts as an AND split (the course allows that implicit split); a parallel join on a loop gets its own message (deadlock). P08 is info only (the course allows an XOR join straight into a task). P09: one word, a first word ending like a noun (-tion, -ment, -al…), an -ing form, a generic verb (do, handle, process, manage, perform), more than 5 words, a small first letter. P15 "pool without lanes" only with `expectLanes` (a case that names roles). Issues are a question, not a verdict: the Check panel is opened by the user, marks on shapes show only while it is open.
- 2026-10-15 ✱ **Help cards** in `src/data/help.ts` (content CC BY-NC-SA), shown in the right column instead of Properties; mini models are a small left-to-right token string drawn as SVG. `?` next to every property field and panel title, F1 or `?` opens the list.
- 2026-10-15 ✱ **Top bar and status bar** (owner's request): top bar left = File menu (New, Open, Save, Save as, Export BPMN, example), Auto layout, Check with a count; centre = the process name (click shows its properties); right = Update (only when a new version waits), Help menu (cards, how to draw, install, about + version), theme. Status bar left = where the work is kept (browser, time); centre = the check summary (click opens the Check panel); right = page, steps, selection, version. The Update button existed in `pwa/register.ts` since stage 0 but was never shown: an installed app never offered updates before v0.3.0 (it still updated on a later start, once all windows were closed).
- 2026-10-15 ✱ **Sub-processes as pages, as in Bizagi** (Bizagi Modeler help: Transform to sub-process, then Edit Sub-Process opens its diagram on a tab; a collapsed sub-process shows +, its details in a separate diagram). Group into sub-process now makes a **collapsed** sub-process; double-click (or Open sub-process) shows its page with a path bar back to the process. Collapse / expand (`setCollapsed`) gives back or takes the width, moving what is right of it, and brings the steps to where the sub-process now is. Steps drawn on a page belong to that sub-process and take its pool and lane, wherever the main canvas has shapes at those coordinates (`pageOf`, `addNode(…, page)`); grouping on a page makes a sub-process inside it without touching the main canvas. Data and notes linked only to the grouped steps go with them. **Export: a collapsed embedded sub-process with its content in a BPMN diagram of its own** (what bpmn.io does) opens in Bizagi exactly that way: + on the main diagram, a tab with the steps (owner's check of two test files). Bizagi's own encoding in one file (a call activity, the sub-process as a separate process in its own pool and collaboration) did not work: Bizagi drew the pool over the main diagram and asked to create a new process.

- 2026-10-15 ✱ **Own cases 1–3** (`cases/`). Each reference model is drawn with the editor's ops in `tests/fixtures/cases.ts` (the shop reuses `order-fulfilment.ts`), laid out by Auto layout and saved as `cases/<id>.flow.json`; `tests/cases.test.ts` checks the file against the drawing (`UPDATE_CASES=1` rewrites it) and that the `.md` has the 7 sections and names every pool, lane and step in section 4. The files lint clean with `expectLanes` and round-trip. Case 1 has no customer pool (pools talking come in case 2). A step that only sends and then ends is a message end event (course rule), so the shop's "Reject order" + end became **Order rejected** (message end) and the reminder became **Reminder sent**. The payment deadline sits on a **receive task** "Receive payment" (a timer boundary event needs an activity; the stage 1 fixture had it on the send task "Send invoice", where it could never fire); the event-based alternative is left to case 4. Arrival of a hotel guest is a catching message event (a message is anything one participant gives another).
- 2026-10-15 ✱ **Context menu and "Change type"** (owner's question: right-click the timer event to change its trigger). Both ways the products use, sharing one list of entries (`src/ui/canvas/menu.ts`): right-click on the canvas as in Bizagi (submenus Trigger, Position, Direction, Interrupting for an event; Task type, Convert to sub-process, Add boundary event for a task; Gateway kind; Default flow and Reverse for a flow; Rename F2, Help card, Delete for all; Group into sub-process for several; Add here, Auto layout, Check on the empty canvas), and a wrench on the context pad as in bpmn.io that opens only the change-type part (touch screens, people who do not know about right-click). The triggers allowed per position moved from Properties to the core (`TRIGGERS`, `triggersFor`); `updateNode` now refuses a trigger not allowed there and gives an event moved to a place where its trigger is not allowed the first allowed one ("none"). - 2026-10-15 ✱ **Trainer (stage 4)**, StrataSQL's pattern. Cases in `src/data/cases.ts` (text = section 2 of `cases/<id>.md`, checked by a test; phrases with tag, target element names and why; synonyms; a coarse step for several, "Lend book"); the reference is the case's `.flow.json`. Eight tags: Pool, Lane, Task, Event, XOR, AND, Message, Data (a phrase may accept several: "sends the invoice" is a task and a message). Level 2 starts from the reference's pools, lanes and tasks (events, gateways, flows and data removed). The user's own model waits in the editor store (`backup`, kept under `strataflow.model` while the task's model goes to `strataflow.trainer.model`); Leave task, New and Open end the task; the session survives a reload. The trainer is a column left of the canvas, so Properties stays on the right.
- 2026-10-15 ✱ **Comparison** (`core/compare.ts`) instead of a full behavioural profile: steps matched by name (stemmed word overlap ≥ 0.5, synonyms), then by place (the same neighbours: "different", asks to rename); start events by pool, end events by the step before, boundary events by host. Order = **links**: which step comes right after which, looking through gateways, so other gateways with the same effect count as right. Decisions: a split whose branches reach the mapped first steps, kind compared (a task with several flows out counts as an AND split). Accepted alternatives: send task for a throwing message event (and the plain end event after it), receive task for a catching one. Lanes by name or by the steps in them; a black-box pool drawn with steps is "different"; message flows by their ends (a step inside an outside pool counts like its border). Score = right + half of "different" minus a quarter per extra, over the reference items. Layout is ignored.

- 2026-10-15 ✱ **Stage 6 before course Chapter 6 arrives** (owner's question): the course follows Dumas et al., Fundamentals of BPM, so its quantitative analysis is the book's flow analysis, a standard method; built from it now, to be checked against the slides later (stage 6b).
- 2026-10-15 ✱ **Flow analysis, not simulation, first** (`core/analysis.ts`): exact averages a student can check by hand (the course's exercises are hand calculations). Sequence adds, a decision weights by probability, a parallel split takes the longest branch for time and the sum for cost (matching join = the nearest node every branch reaches), loops by iterating the expected values until they settle (a rework loop gives T / (1 − r)); a loop no case leaves gives no number and a note. Sub-processes count their content, repeats multiply (parallel instances: the time of one, the cost of all). Branches without a probability share what the others leave; a sum other than 100 % is scaled, with a note. Efficiency = processing / cycle time. Lanes are resource pools: utilisation = arrivals × work per case / capacity. Boundary-event paths and waits for other pools are not counted (notes say so). Queues from resource contention = stage 6b.
- 2026-10-15 ✱ **Waiting time is typed** on the activity that waits (tray, mail, batch run), as Bizagi's time analysis does; a catching intermediate event can wait too.
